# RFC: Classification Approach for Bias Lens
 
**Project:** Bias Lens (Project 007)  
**Author:** Harry Yu  
**Date:** November 23, 2026  
**Status:** Proposed  
**Decision:** Begin with an existing LLM guided by versioned definitions, examples, and structured output requirements; do not fine-tune initially. Reconsider after expert-reviewed evaluation.
 
## 1. Problem and Context
 
Bias Lens is a capstone project for a sponsor who works with counseling transcripts. It helps clients and therapists review transcripts for bias. It has three parts: a rule-based baseline detector, a model-based classifier scored against human-annotated labels, and a clinician review interface showing each flag's evidence. The decision is how to build the classifier: fine-tune an open-weight model, or prompt an existing one.
 
The team listed custom model training as hard to reverse in an earlier workshop [R1]. Three other things are hard to undo. First, transcripts sent to a third-party hosted model cannot be recalled, and the project is under an NDA. Second, annotation is scarce, and labels are collected in a format shaped by the approach (training examples or an evaluation set). Third, the interface and database will be built around the classifier's output format (spans, confidence scores, rationales). This RFC treats those three as the decision.
 
False positives could unfairly flag appropriate therapist responses, and false negatives would leave real bias unflagged. The decision is needed now because the team is about to design the annotation format and the classifier's output contract. The project partner approved Claude Code, GitHub Copilot, and Replit for writing code and testing [R5], but not yet for sending transcripts to a hosted model, so the data question stays open. If the team does nothing, annotation and interface work proceed without a classifier plan, and each choice gets made implicitly by whoever builds that piece first.
 
## 2. Options
 
Two choices run through these options. Whether to use a model at all is the choice between A and the others. Where the model runs (a third-party host or hardware the team controls) is a separate choice that applies to C, since B is always local.
 
### Option A: Do nothing (build only the rule-based baseline, defer the model)
 
The team builds and scores the rule-based detector and postpones the model-based classifier.
 
**Benefits:** No sensitive data goes to any model. There is no training or prompt cost, and the baseline is fully inspectable and reproducible.
 
**Costs:** The project plan calls for a model-based classifier compared against the baseline, so the main evaluation would be missing. Keyword-style rules are likely to miss implicit or context-dependent bias.
 
**Right when:** the sponsor accepts a rule-based result as the deliverable, or approval to use any model on the data cannot be obtained this term.
 
### Option B: Fine-tune an open-weight LLM
 
The team trains an open-weight model (one whose weights can be downloaded and run locally) on its annotated spans, for example with LoRA, which adapts a small set of added parameters instead of the whole model [S2]. It runs on hardware the team controls.
 
**Benefits:** Transcripts never leave team-controlled hardware, which fits the NDA. Weights can be pinned, so results are reproducible. A trained model can learn the sponsor's fine distinctions instead of relying on a description of them.
 
**Costs:** It needs enough labeled examples per category, and annotation is the scarcest resource. Every taxonomy change means retraining and re-evaluating. Open-weight licenses differ, and a small training set can overfit and fail on new transcripts.
 
**Right when:** the taxonomy is stable, there is enough labeled data and compute access, and a pilot shows that prompting a model on controlled hardware does not meet the accuracy bar.
 
### Option C: Use an existing LLM with structured instructions
 
The team writes a prompt with definitions of each category, a few worked examples, and a required output schema, then runs a general-purpose model with no training, either hosted by a third party or as an open-weight model on hardware the team controls.
 
**Benefits:** It works with a small labeled set, since labels are needed mainly to evaluate, not to train. Changing a category is a prompt edit, not a retraining run. It can be tried early on synthetic transcripts.
 
**Costs:** If hosted, transcripts leave the team's control, which depends on the project partner’s approval. Hosted models can change or be retired, so results may not be reproducible later. If local, the team must run and secure the model. Outputs can be sensitive to wording and format failures must be handled.
 
**Right when:** labeled data is scarce, categories are still changing, and either the sponsor approves a hosted tool for this data, or the team can run an open-weight model locally.
 
## 3. Analysis
 
### Performance and data needed
 
Few-shot prompting lets large language models perform new tasks from instructions and a handful of examples, with no training [S1]. That is the mechanism Option C relies on, but the paper shows general capability, not that it works on this task. Fine-tuning needs enough labeled examples to learn each category. LoRA reduces the compute and memory needed to adapt a large model [S2], which makes Option B feasible on limited hardware, but it does not reduce the amount of labeled data needed.
 
I have not measured either approach on this project, so I cannot say which would be more accurate on the sponsor's categories. The repository currently has a turn splitter and an LLM adapter interface with a fake adapter and tests (PR #4), documentation of the instructions and examples to be given to the model (PR #7), and an end-to-end backend pipeline on synthetic transcripts with an Anthropic adapter and upload and detect routes (PR #8) [R2]. The flag validator (PR #8) checks output structure, not whether flags are correct, so no accuracy measurement exists yet. How many labeled examples per category the team will end up with is the largest uncertainty in the choice between B and C.
 
### Reproducibility and drift
 
A published study found that the behavior of hosted LLM services changed noticeably over a few months on the same tasks [S3]. If the team uses a hosted model for Option C, scores measured now may not be reproducible later. The team should pin and record the model version with every result, or use a model it can run itself. Option B avoids this by pinning weights.
 
### Confidentiality and security
 
This is the main reason the decision is hard to reverse. Transcripts sent to a hosted model cannot be recalled, and the project is under an NDA. The team charter defines data tiers for what may be pasted into AI tools [R4]. Option B keeps all data local. Option C is acceptable only with a tool approved for that tier, or run locally. The ADR guide used in this course says to write an ADR for decisions that are expensive to reverse [S4], and irreversible disclosure of data is the clearest example in this project.
 
### Complexity and maintainability
 
The stack (React/Vite/TypeScript, Express, PostgreSQL with Drizzle, and Clerk for authentication [R3]) does not constrain the choice. Option B adds a training pipeline, hardware needs, and model storage. Option C adds prompt files that should be versioned in the repository like code.
 
The review interface's output contract (span, category, confidence, rationale) can be the same for both. If the team defines that contract first, either approach can fill it, which keeps the choice reversible.
 
### Interaction with the taxonomy
 
The bias categories are being decided separately. Prompting tolerates changes to them much better than fine-tuning does, because a prompt edit is cheap and a retrain is not.
 
### Cost
 
Option C on a hosted model has a per-use cost that grows with corpus size. Option B has an up-front compute cost plus storage and access control for the weights. I have not priced either option. The first prototype should record token usage, run time, and hardware needs, so the comparison rests on measurement.
 
## 4. Recommendation and Verification Plan
 
I recommend Option C. Labeled data is scarce, the taxonomy is not final, and prompting is faster to evaluate and cheaper to change than fine-tuning (Section 3). The team should develop and tune the prompt on synthetic transcripts. It should run real or de-identified transcripts only through a tool approved in writing for that data tier, or a locally hosted model. This keeps the hard-to-reverse parts under control: no data leaves without approval. I have not measured this approach, so the checks below are how the team finds out whether it works.
 
| Check | How it is run | Pass | Failure means |
|---|---|---|---|
| Approval gate | Before any tool touches real or de-identified transcripts, the team records the tool, data tier, and the sponsor's written approval in docs/. Synthetic data needs no approval. | Every tool used on non-synthetic data has approval on file. | A transcript was processed without recorded approval. Stop work and tell the sponsor. |
| Schema validity | An automated test in the repository validates every output (valid format, category from the taxonomy, span inside the transcript). | At least 95% of outputs on held-out transcripts validate. Invalid outputs count as misses in check 3. | Fix the prompt or output handling before judging accuracy. |
| Accuracy against humans | Run on a held-out, human-annotated set that was never used in prompts or tuning. Report per-category precision, recall, and counts, and compare them with the rule-based baseline and with agreement between annotators (Cohen's kappa). | Proposed: precision ≥ 0.80 and recall ≥ 0.70 per category, recall above the baseline, and kappa within 0.10 of annotator-to-annotator kappa. The team fixes these in writing before the first held-out run. A category with fewer than 20 held-out examples is reported as "not enough data," not as passed. | Apply the triggers below. |
| Stability | Run the same held-out inputs twice with the model version pinned and the lowest-randomness settings. | At least 95% of labels are identical across runs. | The prompt or model is unstable. Clarify the prompt or change the model. |
 
**Triggers:** If a category is still below the bar on the held-out set after two prompt revisions made on a separate development set, and at least [100] reviewed examples of it exist, the team evaluates fine-tuning that category (Option B), subject to a license and compute check. If the project partner’s approval for any model on real data is not in place by the end of week 10 of fall term, the team ships the baseline (Option A) and reports Option C results on synthetic data only.
 
**When:** Checks 1, 2, and 4 run on the first prototype using synthetic data. Check 3 runs on the held-out set after the first full labeling pass. Until check 3 has run, the decision stays Proposed.
 
## 5. Constraints
 
**Confidentiality and NDA.** The project is under an NDA, so this RFC refers to the project partner generically. Any outside tool used on transcript data needs the project partner’s written approval, and nothing leaves the team's control without it.
 
*What it changes:* The partner approved Claude Code, GitHub Copilot, and Replit for writing code and tests only [R5]. Hosted Option C is therefore ruled out for real or de-identified transcripts until written approval is on file for the tool and data tier. If approval is not in place by the end of week 10 of fall term, the team falls back to Option A.
 
**Data use.** Only de-identified or synthetic transcripts may be used, and the source of real transcripts is still pending written terms. Prompts, logs, and training sets built from transcripts are sensitive derivatives and are stored under the same restrictions. Transcript text is never pasted into an unapproved AI tool.
 
*What it changes:* Development and tuning use synthetic data only. Under Option B, the training set and trained weights need access controls. Under Option C, prompt logs do too, and none of these go in the repository.
 
**Licensing and provider terms.** Each model needs a license that permits this use, and open-weight licenses vary. Hosted tools are bound by their provider's terms, including how they retain inputs or use them for training.
 
*What it changes:* Reading the chosen model's license is a required step before the team commits to Option B or a local Option C. For a hosted tool, the team reads the provider's data-retention terms before requesting approval.
 
**Use restriction.** The tool may not be used to evaluate individual clinicians or to inform employment or licensure decisions, according to our project partner [R5].
 
*What it changes:* Prompts and outputs describe language markers, not judgments about a clinician. This wording is part of the output contract and the review interface.

**What checks made that reasonable:** This RFC is a document, and nothing hard to reverse has been built, so the checks are on its content: each cited source was opened and read, and the repository evidence was checked against the repository. The code in PRs #4 and #8 ran under automated tests and a type check.
 
**Where I stopped and validated myself, and why.**
 
- **References.** I opened each reference and confirmed it says what the RFC claims. A reference that doesn't exist or doesn't say this is an invented-evidence failure.
- **Approval scope.** I read the project partner's written approval to confirm which tools are approved and for what. Sending transcripts to an unapproved hosted model can't be undone and would breach the NDA.
- **Thresholds.** I reviewed and adopted the precision, recall, and stability targets in Section 4. If the bar is wrong, a weak classifier could pass, and the annotation format would be built around it.
- **Repository evidence.** I confirmed that PRs #4, #7, and #8 exist and say what Section 3 describes.
## 7. Decision
 
**Status:** Proposed. **Deciders:** Jack Stanfield, Da’Meka Bell, Harry Yu, and our project partner. **Decision date:** end of week 10 of fall term.
 
The recommendation is Option C. The rule-based baseline stays as the comparison point. The review interface's output contract is defined independently of the model, so the model can be swapped later without rebuilding the interface.
 
What would make it Accepted:
 
- The project partner's written approval states which tools may process which transcripts (first check in Section 4).
- The team agrees on the taxonomy and the annotation format.
- The team commits the thresholds for the third check before the first held-out run.
What would change it: The team evaluates Option B for a category that stays below the bar after two prompt revisions, once enough reviewed examples exist. It falls back to Option A if approval is not in place by the end of week 10 of fall term.
