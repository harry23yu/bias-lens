## Problem and Context

Bias Lens is a capstone project for a sponsor who works with counseling transcripts. The system flags bias markers in those transcripts. The project plan has a rule-based baseline detector, a model-based classifier scored against human-annotated labels (per-category precision and recall), and a clinician review interface. The team has not yet decided how the model-based classifier will be built. The two realistic routes are to fine-tune an open-weight LLM on the team's annotated data, or to use an existing LLM with structured instructions (a written prompt with category definitions, examples, and a required output format) and no training.

The team listed custom model training as a hard-to-reverse decision in its Workshop 2 submission. The model swap itself is not what is hard to undo, because a prompt can be replaced by a fine-tuned model later and the reverse is also possible. Three other things are hard to undo. First, if transcripts, even de-identified ones, are sent to a third-party hosted model, they cannot be recalled, and the project is under an NDA. Second, annotation is the scarcest resource, and the labels will be collected in a format shaped by the approach: training examples for fine-tuning, or an evaluation set for prompting. Third, the review interface and database will be built around the classifier's output format (for example, spans, confidence scores, and rationales). This RFC treats those three as the decision, and the model as the visible part of it.

The decision is needed now because the team is about to design the annotation format and the classifier's output contract, and because using any outside tool on sensitive data needs the sponsor's written approval first. If the team does nothing, it reaches the annotation and interface work without a classifier plan, so each choice gets made implicitly by whoever builds that piece first. The team has also not confirmed that this decision is still open.

## Options

### ### Option A: Do Nothing (rule-based baseline only, defer any model)

The team builds and scores the rule-based detector and postpones the model-based classifier.
 
- **Benefits:** No sensitive data goes to any model. No training or prompt cost, and the baseline is fully inspectable and reproducible.
- **Costs:** The project plan calls for a model-based classifier compared against the baseline, so the main evaluation would be missing. Rules are likely to miss implicit or context-dependent bias, which is a known weakness of keyword-style rules. The decision also arrives anyway, later, with less time left.
- **Right when:** the sponsor accepts a rule-based result as the deliverable, or approval to use any model on the data cannot be obtained this term.

### Option B: Fine-tune an existing open-weight LLM

The team trains an open-weight model (for example with parameter-efficient methods such as LoRA) on its annotated spans, and runs it on hardware the team controls.
 
- **Benefits:** Transcripts never leave team-controlled hardware, which fits the NDA. Model weights can be pinned, so results are reproducible. A trained model can learn the sponsor's fine distinctions rather than relying on a description of them.
- **Costs:** It needs enough labeled examples per category, and annotation is the scarcest resource here. Every change to the taxonomy means retraining and re-evaluating. Open-weight licenses differ in what they allow, so the chosen model's license has to be read before use. A small training set can overfit and produce results that look good on the training data and fail on new transcripts.
- **Right when:** the team has a stable taxonomy, enough labeled data, compute access, and a requirement that data stays on controlled hardware.

### Option C: Use an existing LLM with structured instructions

The team writes a prompt containing definitions of each category, a few worked examples, and a required output schema, and runs a general-purpose model with no training.
 
- **Benefits:** It works with a small labeled set, since labels are needed mainly to evaluate, not to train. Changing a category is a prompt edit, not a retraining run. It can be prototyped on synthetic transcripts within days.
- **Costs:** If the model is hosted by a third party, transcripts leave the team's control, which depends on the sponsor's approval and on the team's data tiers. Hosted models can change or be retired, so results may not be reproducible later. Outputs can be sensitive to wording, and output-format failures must be handled. Per-use cost accrues over a large corpus.
- **Right when:** labeled data is scarce, categories are still changing, and the sponsor approves a tool for this data (or the team runs an open-weight model locally without training it).

## Analysis

**Data needed.** Few-shot prompting was shown to let large language models perform new tasks from instructions and a handful of examples without gradient updates, which is the mechanism Option C relies on. Fine-tuning needs enough labeled examples to learn each category. Parameter-efficient methods such as LoRA reduce the compute and memory needed to adapt a large model, which makes Option B more feasible on limited hardware, but they do not reduce the amount of labeled data needed. I have not measured either approach on this project, so I do not know how many labeled examples per category the team will end up with, and that number is the largest uncertainty in the choice between B and C.
 
**Reproducibility and drift.** A published study found that the behavior of hosted LLM services changed noticeably between versions over a few months on the same tasks. If the team uses a hosted model for Option C, scores measured now may not be reproducible later, so the model version must be pinned and recorded with every result, or the team should use a model it can run itself. Option B avoids this by pinning weights.
 
**Confidentiality.** This is the main reason the decision is hard to reverse. The team's charter defines data tiers for what may be pasted into AI tools. Option B keeps all data local. Option C is acceptable only with a tool approved for that tier, or run locally. The ADR guide used in this course says to write an ADR for decisions that are expensive to reverse (ADR guide, "Which Decisions Deserve an ADR?"), and an irreversible disclosure of data is the clearest example in this project.
 
**Complexity and maintainability.** The stack (React/Vite/TypeScript, Express, PostgreSQL with Drizzle, Clerk. (See README.md)) does not constrain the choice. Option B adds a training pipeline, hardware needs, and model storage. Option C adds prompt files that should be versioned in the repository like code. The review interface's output contract (span, category, confidence, rationale) can be the same for both, which is one way to keep the choice reversible: define that contract first, and either approach can fill it.
 
**Interaction with the taxonomy.** The bias categories are being decided separately. Prompting tolerates changes to them much better than fine-tuning does, because a prompt change is cheap and a retrain is not.
 
**Security and cost.** Option C on a hosted model has a per-use cost and a data-egress risk. Option B has an up-front compute cost and a storage and access-control requirement for the trained weights, which are derived from sensitive data and should be treated as sensitive too.

## Recommendation and Verification Plan

I recommend **Option C**, run either through a tool the sponsor has approved in writing for this data tier or through an open-weight model hosted locally without fine-tuning, with a defined trigger to move to Option B. It wins on this analysis because labeled data is scarce, the taxonomy is not final, and prompting is faster to evaluate and much cheaper to change. It also keeps the hard-to-reverse parts under control: no data leaves without approval, and the output contract is defined independently of the model.
 
**How the team will know it worked** (bracketed values are the team's to set):
 
1. **Approval gate:** before any real or de-identified transcript is sent to any tool, the sponsor's written approval is on file. Failure looks like a transcript processed by a tool with no recorded approval, which stops the work.
2. **Schema validity:** the classifier's output parses against the required schema on at least (let's say for now, 95%) of held-out transcripts. A test in the repository runs this check.
3. **Accuracy against humans:** on a held-out, human-annotated set, report per-category precision and recall for the baseline and the classifier. The classifier is judged against the baseline and against human-to-human agreement, and the team sets the minimum bar before looking at results.
4. **Stability:** the same inputs run twice, with the model version pinned, give the same labels at least 95% percent of the time. Failure shows prompt or model instability.

These are checked when the first prototype runs on synthetic data, and again after the first full labeling pass.

## Constraints

- **Confidentiality / NDA:** the project is under an NDA. This RFC contains no sponsor-confidential specifics and refers to the sponsor generically. Any outside tool used on project data needs prior written approval from the sponsor, and nothing leaves the team's control without it.
- **Data use:** only de-identified or synthetic transcripts may be used. The source of the transcripts is still an open decision pending written terms, and prompts, logs, and training sets built from transcripts are sensitive derivatives and must be stored with the same restrictions. Transcript text must never be pasted into an unapproved AI tool.
- **Licensing:** “Each model used needs a license that permits this use. Open-weight licenses vary, so the chosen model’s license must be read before it is chosen. Hosted tools are bound by their terms of service.”
- **Use restriction:** “The tool may not evaluate individual clinicians or inform employment or licensure decisions, so prompts and outputs describe language markers, not clinician judgments.”
- **IP:** “Ownership of project outputs, including any trained weights, is governed by the course and sponsor IP policy, not by this decision.”
